# 服务端部署指南

本文面向希望自行托管 Many Fish 的使用者，涵盖首次部署、HTTPS 配置、证书续期和版本更新。我们提供的服务端发布包可以直接运行，无需安装 npm 运行依赖。

以下以 Ubuntu/Debian、Node.js 18+、systemd 服务名 `card` 为例，推荐使用 Node.js 24 LTS。当前公开 Demo 为 `0.1.0-demo.2`，内部 HTTP 端口为8080，HTTPS 示例端口为8443。示例 IP `203.0.113.10` 必须在执行前统一替换为部署服务器的公网 IP。

客户端提供“官方服务器”选项；自建服务可通过“自定义服务端”连接，也可以让玩家直接访问部署后的网页。已经完成部署的使用者可跳至 [更新现有服务器](#更新现有服务器)。

## 1. 准备运行文件

使用 `dist/fish-server-update.zip`，解压后的结构应为：

```text
server.mjs
src/
public/
release.json
LICENSE
README.md
docs/服务端部署.md
scripts/build-release.mjs
package.json
package-lock.json
dist/fish-source.zip
```

不要遗漏 `src/`、`public/release.json` 或根目录 `release.json`；所有文件必须来自同一发布包。运行无需 `npm install`，Linux 不需要 Windows 启动脚本和 `.msi`。

检查 Node 是否满足要求：

```sh
node --version
command -v node
```

缺少环境时按 [Node.js 官方安装入口](https://nodejs.org/en/download)安装当前 LTS，完成后重新检查。下文 `ExecStart=/usr/bin/node` 应替换为 `command -v node` 显示的绝对路径。

本指南使用 `/etc/fish` 作为游戏目录。首次部署时创建该目录；更新已有服务时，以现有 systemd 配置中的目录为准：

```sh
sudo install -d -m 755 /etc/fish
```

将服务端包完整上传并解压到该目录，保留文件内容、换行和子目录结构。

## 2. 建立 systemd 服务

首次部署可创建专用运行用户，并让它读取游戏目录：

```sh
id tide-card || sudo useradd --system --no-create-home --shell /usr/sbin/nologin tide-card
sudo chown -R tide-card:tide-card /etc/fish
sudo nano /etc/systemd/system/card.service
```

写入以下配置，按实际目录和 Node 路径修改：

```ini
[Unit]
Description=Many Fish Demo
After=network.target

[Service]
Type=simple
User=tide-card
WorkingDirectory=/etc/fish
ExecStart=/usr/bin/node /etc/fish/server.mjs
Environment=NODE_ENV=production
Environment=PORT=8080
Environment=HOST=127.0.0.1
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

`HOST=127.0.0.1` 适合下面的 Nginx 反向代理部署；只对本机监听。直接进行局域网测试时使用默认 `0.0.0.0`，并允许专用网络访问8080端口。

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now card
sudo systemctl status card --no-pager
curl http://127.0.0.1:8080/api/health
```

正常返回包含 `ok: true`、`version: "0.1.0-demo.2"`、`integrity: "verified"` 和发布摘要。

若出现 `status=200/CHDIR`，检查 `WorkingDirectory` 是否存在、运行用户是否有读取和进入目录的权限，以及 `ExecStart` 是否指向同一目录。修改 unit 后需要再次 `daemon-reload`。

## 3. 没有域名时配置免费 HTTPS

Let's Encrypt 支持公网 IP 证书；IP 证书使用约六天有效期的短期配置。Certbot 的 IP `webroot` 模式需要5.4或更新版本，必须配好自动续期和 Nginx 重新加载。[官方说明](https://letsencrypt.org/2026/03/11/shorter-certs-certbot)

服务器需要固定公网 IP，且 TCP 80可从外网访问。本文使用8443作为 HTTPS 端口；如果443可用，也可以使用标准 HTTPS 端口443，并同步修改重定向、监听、访问网址和防火墙。

### 安装 Nginx 并开放挑战路径

```sh
sudo apt update
sudo apt install nginx snapd
sudo install -d -m 755 /var/www/letsencrypt/.well-known/acme-challenge
sudo nano /etc/nginx/conf.d/tide-card-ip.conf
```

先写入临时 HTTP 配置，将示例 IP 替换为部署服务器的公网 IP：

```nginx
server {
    listen 80;
    server_name 203.0.113.10;

    location ^~ /.well-known/acme-challenge/ {
        root /var/www/letsencrypt;
        default_type text/plain;
        try_files $uri =404;
    }

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_buffering off;
        proxy_read_timeout 1h;
    }
}
```

```sh
sudo nginx -t
sudo systemctl enable --now nginx
sudo systemctl reload nginx
printf 'ok\n' | sudo tee /var/www/letsencrypt/.well-known/acme-challenge/check.txt
curl http://203.0.113.10/.well-known/acme-challenge/check.txt
```

应返回 `ok`，还应从另一台设备或网络确认可访问。云安全组与系统防火墙需开放80及8443，保留 SSH 端口。启用 UFW 的服务器可按实际情况设置：

```sh
sudo ufw allow 80/tcp
sudo ufw allow 8443/tcp
```

### 申请正式 IP 证书

```sh
sudo snap install --classic certbot
/snap/bin/certbot --version
sudo /snap/bin/certbot certonly \
  --preferred-profile shortlived \
  --webroot \
  --webroot-path /var/www/letsencrypt \
  --ip-address 203.0.113.10 \
  --cert-name tide-card-ip
sudo /snap/bin/certbot certificates
```

按提示完成邮箱和服务条款。已有 Certbot 时保留原安装方式；snap 安装可用 `sudo snap refresh certbot` 更新。正式证书不要带 `--staging`。证书路径以下列命令实际输出为准。

### 配置 HTTPS

将上述站点文件替换为：

```nginx
server {
    listen 80;
    server_name 203.0.113.10;

    location ^~ /.well-known/acme-challenge/ {
        root /var/www/letsencrypt;
        default_type text/plain;
        try_files $uri =404;
    }

    location / {
        return 301 https://$host:8443$request_uri;
    }
}

server {
    listen 8443 ssl default_server;
    server_name 203.0.113.10;

    ssl_certificate /etc/letsencrypt/live/tide-card-ip/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/tide-card-ip/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_buffering off;
        proxy_read_timeout 1h;
    }
}
```

`proxy_buffering off` 让 SSE 对局更新及时送达。`default_server` 让以 IP 访问且没有域名 SNI 的连接收到该 IP 证书，同一监听地址不能重复设置默认站点。

```sh
sudo ss -ltnp | grep ':8443'
sudo nginx -t
sudo systemctl reload nginx
curl -i https://203.0.113.10:8443/api/health
```

如果8443已被其他服务占用，先选择空闲端口。修改 Nginx 的监听端口时使用 `sudo systemctl restart nginx`，并再次检查监听进程。玩家连接自建服务时，选择“自定义服务端”并填写完整地址，例如 `https://203.0.113.10:8443`；直接访问该地址的玩家选择“当前页面的服务端”即可。

需要分发预设自建地址的客户端时，可修改 `public/js/config.mjs` 中的服务器配置，再按 README 中的开发与发布流程重新生成发布包。

浏览器应能无证书警告打开游戏。8080无需公网开放，Nginx 通过127.0.0.1连接 Node。

## 4. 自动续期及验证

续期后必须让 Nginx 加载新证书。创建部署钩子：

```sh
sudo install -d -m 755 /etc/letsencrypt/renewal-hooks/deploy
sudo tee /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh >/dev/null <<'EOF'
#!/bin/sh
set -e
/usr/bin/systemctl reload nginx
EOF
sudo chmod 755 /etc/letsencrypt/renewal-hooks/deploy/reload-nginx.sh
systemctl list-timers --all | grep -i certbot
sudo /snap/bin/certbot renew --dry-run --run-deploy-hooks
sudo journalctl -u nginx --since "10 minutes ago" --no-pager
```

定时任务存在、续期演练成功，且日志出现 Nginx Reloaded，即说明定时续期和成功后的证书加载链路已验证。演练不会替换正式证书，不能保证未来的网络一直可用；80端口和挑战路径需长期保持可访问。[Certbot 续期与部署钩子](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates)

## 更新现有服务器

1. 在当前对局结束后更新；重启会清空全部房间。
2. 查出现有目录和启动路径，不要凭示例覆盖其他目录：

   ```sh
   systemctl show card -p WorkingDirectory -p ExecStart
   ```

3. 备份整个游戏目录和 unit，停止 `card`。完整覆盖新服务端包，特别是 `src/`、`public/`、根目录 `release.json`、`LICENSE` 和 `dist/fish-source.zip`。新 `server.mjs` 仍在根目录，已有 `ExecStart` 可继续使用。旧根目录的 `engine.mjs`、`room-store.mjs`、`release-integrity.mjs` 已不再使用，备份后可清理。

   ```sh
   sudo systemctl stop card
   ```

4. 确认服务运行用户可读取新文件，重启并检查：

   ```sh
   sudo systemctl restart card
   sudo systemctl status card --no-pager
   curl http://127.0.0.1:8080/api/health
   curl -o /dev/null -w '%{http_code}\n' https://203.0.113.10:8443/LICENSE
   curl -o /dev/null -w '%{http_code}\n' https://203.0.113.10:8443/source.zip
   ```

   两个下载地址应返回200；也可用浏览器查看许可证和保存源码包。

5. 玩家更新 Windows 包、重启本地启动脚本，再按 `Ctrl+F5` 刷新。直接访问服务器网页的玩家刷新即可。双方必须匹配同一发布，不能只改版本号或只上传一两个文件。

6. 检查双方入房、手牌、攻击及企鹅挡伤、翻车鱼每回合限一次、保留恢复和结算返回；确认底部许可证与源码链接可用。

## 校验、修改版与源码

服务端启动时核对发布清单里的运行文件，客户端入房前核对网页文件、规则和发布摘要。启动后发送本次已校验的页面资源；修改源文件后需重新生成清单并重启。

修改和自建服务端是 GPLv3 允许的使用方式。开发副本在格式化、同步版本后执行 `node scripts/build-release.mjs`，再测试和打包。部署服务器按已发布的基线校验，不要在启动时自动重建清单来掩盖上传错误。

网页底部的 `/LICENSE` 提供许可证全文，`/source.zip` 提供包内 `dist/fish-source.zip`。公开部署时保留与运行版本对应的源码下载；当前服务端包已经附带，不需要额外生成。

浏览器摘要可能被伪造，发布清单也不是数字签名。实际防止改客户端规则作弊依靠服务端独立结算；该机制无法证明控制局域网主机的房主可信。

## 故障排查

```sh
sudo journalctl -u card -n 80 --no-pager
sudo journalctl -u nginx -n 80 --no-pager
sudo nginx -t
sudo ss -ltnp
sudo /snap/bin/certbot certificates
```

| 现象             | 检查                                                           |
| ---------------- | -------------------------------------------------------------- |
| 200/CHDIR        | 工作目录、权限和 ExecStart 是否一致                            |
| 文件校验失败     | 完整覆盖同一版本的全部运行文件，保持内容及换行；日志会指出文件 |
| 客户端版本不一致 | 更新服务端和双方客户端，再 Ctrl+F5；规则摘要不同也会拒绝       |
| 服务端不支持校验 | 当前指向旧版服务，完整更新并重启 card                          |
| HTTPS 502        | 内部健康检查、card 状态和 Nginx 代理端口                       |
| 入房后不更新     | SSE 反向代理是否禁用缓冲，游戏服务是否仍运行                   |
| 源码下载404      | `dist/fish-source.zip` 是否存在、运行用户是否可读              |
| 证书与 IP 不匹配 | IP 是否正确，以及真正监听 HTTPS 端口的进程与证书               |

核对证书文件与实际送出的证书：

```sh
sudo openssl x509 -in /etc/letsencrypt/live/tide-card-ip/fullchain.pem -noout -ext subjectAltName
echo | openssl s_client -connect 127.0.0.1:8443 2>/dev/null | openssl x509 -noout -ext subjectAltName
```

两处应包含部署服务器的 `IP Address`。若磁盘证书正确而实际证书不同，先用 `ss` 找到占用端口的程序，再修正 Nginx 配置和端口；不要用忽略证书错误代替修复。
